# 大文本真实输入与窗口缩放验证

2026-10-21。前半部分保留 SourceView `0c1eb4b` 与 GOUI `4018c7a` 的实际桌面
操作基线；当时只增加验证程序。后续生产修正与复测见末尾的“修正后的结果”。

多行 SourceView 的编辑与缩放可用，但不等于已经没有卡顿；128 KB 单段落仍有明显
同步耗时。TextView 的同规模单段落缩放响应验收失败，54 MB JSON 未能进入编辑
阶段。以下分别记录操作延迟、GUI 事件间隔和不能完成的场景。

## 测量方法

`tests/window/editor/interaction/main.go` 创建 Modern、WindowChromeIntegrated
窗口，在 ScrollView 中显示完整输入文件并启用自动换行。SourceView 保留行号、
折叠和编辑辅助，仅关闭自动补全，避免弹窗改变本轮键盘操作目标。
`-kind text` 改为 GOUI TextView，使用其默认字体；这不是两控件的等字体性能对比。

`desktop.py` 在另一个进程中，通过 XTest 向 X11 发送正常按键、鼠标和连续拖拽。
普通字符走系统文本输入通道；粘贴使用真实 CLIPBOARD 和 Ctrl+V；删除、选区、
撤销与重做使用实际按键。脚本没有调用编辑、选区、尺寸或事件分发的 Go 接口。
窗口移动、激活仅用于准备；计时中的缩放拖动真正的窗口边框和右下角。

起点是发送桌面输入前，终点是 XGetImage 从桌面根窗口读到已更新的可见状态条。
状态条位于正文后面的最后一个 Paint，包含输入序号、文档 revision、选区、字节数、
视口大小及 SourceView 的 `layoutPending`；它只被动显示诊断值，不接受命令。
编辑完成要求实际字节数、光标与独立预期一致，且该帧视区排版不再 pending。
这包含输入排队、实际修改、延后排版、绘制和 X11 桌面更新；不是函数返回时间，
也不是物理显示器扫描延迟。语法颜色可能在此之后继续更新。

分别记录输入回显 `echo_ms` 和上述视区就绪帧 `visible_ms`。前者可能先于异步粘贴
结果；普通字符被输入法消费时没有控件 KeyDown，以 revision/选区变化识别回显。
后者是就绪帧的观测时间，不能单独称为连续 UI 阻塞时间。
输入观察器为了显示事件序号会请求绘制；它不修改事件或编辑行为。计时器不请求
绘制，测试也不在等待期间不断强制刷新。结果包含诊断条与采样器的观测开销。

窗口缩放在约 0.5 秒中发送 16 个鼠标位置，记录已呈现的中间视口尺寸、相邻尺寸帧
的最长间隔和松手后的就绪时间。原生窗口管理器的 resize grab 可能消费键盘，
因此不使用拖动中的按键丢失判断窗口冻结。每次断言准确的最终原生窗口尺寸、
光标与文本长度不变；拖动期间至少呈现两次尺寸更新才通过响应验收。该项失败会
保留记录并继续后续缩放/全文校验，最终脚本退出码仍为 1，不伪装成通过。

另有不请求绘制的 10 ms GUI Timer，记录大于 20 ms 的投递间隔，用于辨别就绪等待
期间 GUI 是否仍处理事件。统计时只取与操作区间重叠的静默部分；它包含实际 GUI
工作和系统调度，不等于某个函数的 CPU 时间或严格的不可抢占时间。采样脚本目标
间隔为 5 ms，另记录实际最大采样间隔，避免把观察进程停顿冒充窗口卡顿。

预期文本拼接、剪贴板准备、截图和全文比较均在操作计时之外。每次编辑检查实际
长度、revision 与光标；最后通过普通 Alt+F4 触发关闭处理器，逐字节检查整个模型
恢复原文。启动者必须同时检查脚本和窗口程序退出码，以及 `verified` 日志；
只看到输入送达或窗口启动不算通过。

## 场景和复现

每份文件在文首、滚动条跳至中部后点击的位置、文尾，执行单字符输入、Backspace、
Delete、粘贴短词、选词替换及撤销重做。文首和文尾另粘贴 65,519 bytes 的 Unicode
多行文本；文首选中这些文本后 Delete，并撤销删除、撤销插入恢复原文。
最后分别缩小/恢复宽度、缩小/恢复高度、缩小/恢复宽高，覆盖新约束和原尺寸。

五份外部文件及 54,009,790 bytes 派生 JSON 的来源、哈希见
[前轮语料记录](PlanCorpusLayout.md)。另将同一 TXT 的 CR/LF 替换为空格，按完整
UTF-8 边界截取 131,072 bytes，得到单个自动换行段落；它不是原始下载文档。
不截断实际打开的文件。原始语料、程序二进制、日志和截图均放仓库外。

```bash
go build -o /tmp/source-interaction ./tests/window/editor/interaction
XMODIFIERS=@im=none GOUI_PLAT_PAINTER=software GOUI_PLAT_SCALE=1 \
  /tmp/source-interaction -file /outside/repo/document.json > /tmp/interaction-app.jsonl 2>&1
# 在另一个终端运行；窗口必须独占本轮的桌面输入。
python3 tests/window/editor/interaction/desktop.py \
  --file /outside/repo/document.json --output /tmp/interaction-result
# 等待窗口正常退出，检查两个进程退出码与 app 日志中的 verified。
```

TextView 两条命令均增加 `-kind text` / `--kind text`。需要 libX11、libXtst、
xdotool、xclip；实际桌面截图依赖 Pillow。输入文件只读。测试会聚焦/移动/缩放窗口、
移动指针并短暂占用 CLIPBOARD；尽量恢复原有 UTF-8 文本，不能恢复富文本等其他
格式，不应与人在同一桌面同时操作。失败立即停止该批，不把后续环境错误算作
控件性能结果。脚本具有有限等待，启动者另加进程超时以应对原生调用卡死。

针对单行文档的中部编辑，可以给 `desktop.py` 增加 `--middle-edit`，仍通过真实
滚动条跳转、正文点击、键盘与剪贴板执行修改和撤销，并在正常关闭时校验全文。
它跳过首尾编辑和缩放，记录中的 `scope` 区分 `middle-edit` 与 `full`。
需要定位原生耗时时，给窗口程序增加 `-cpu-profile /outside/repo/new.pprof`；
输出路径必须不存在。此模式还记录超过 3 ms 的创建、尺寸、簇坐标、设色与光栅化
调用。它不接受编辑命令，诊断数据不混入未启用分析器的端到端统计。

## 失败记录及适用边界

最初的诊断程序要求所有字符都有 KeyDown，导致 q 已正常替换但等待超时；已依据
实际文本输入通道修正观察条件。首次 resize 中的 F12 探针被原生 resize grab 消费，
没有作为控件失败；改为观察中间尺寸帧及被动 GUI Timer。保留操作内容和全文断言。

首轮 54 MB JSON 在中部视区等待超过原定 30 秒，暂不能只据此判断冻结；后续使用
更长的观测窗口并独立记录事件循环间隔，不把等待变长描述为性能修复。

1 MiB 的真实剪贴板粘贴另发现失败：曾收到 `clipboard: read timed out`；进一步
核对时，独立 xclip → xclip 的同规模读取也未能通过，因此不能把这次超时的根因
确定归到 GOUI，也不能给出 1 MiB 粘贴的有效延迟。源码
`platform/linux/x11/clipboard_linux.go` 当前只实现非 INCR 读取，并明确拒绝 INCR，
这是已确认的能力边界；完整大剪贴板支持需要另行验证/实现。此项不降低已通过的
64 KB 粘贴、删除或全文恢复的正确性要求。超大剪贴板不作为其他操作的验证读取
通道，全文比较仍完整保留在关闭处理器中。

该早期失败使窗口退出、外部 XGetGeometry 返回 BadDrawable，Xlib 默认错误处理
直接终止观察进程，未能进入 Python finally。现在观察进程捕获 X11 错误并让几何
读取失败正常抛出异常，保证释放鼠标/键盘并尽量恢复剪贴板。不可用的剪贴板读取
显式视为不可恢复，而不无限重试。失败批次的后续剪贴板准备超时不计入性能样本。
部分早期失败时原剪贴板文本不可读取，不能确认其完整恢复；不把尽力恢复记作已
恢复。验证窗口均已关闭，鼠标/修饰键均释放，输入文件与桌面设置没有修改。

底部诊断条在原生 resize 改变裁剪边界时可能先被裁掉，造成漏采中间帧；最终使用
固定在顶部、仍在正文后绘制的 Overlay，避免据此误判冻结。早期底部采样不进入
最终统计。

最初 TextView 窗口还受到自动最小尺寸影响：窗口用已加载文档做无约束首选尺寸
测量，被撑到约三万像素高，违背预定视口。该轮的 5～8 秒数据作废。最终窗口显式
设置最小尺寸 640×360，并在输入前断言实际初始窗口恰为 1100×760。SourceView
前面的语料轮次实际窗口尺寸一直正确，各缩放记录也包含原生窗口尺寸。

## 环境与结果

Linux amd64，X11/XFCE/xfwm4，Pango 1.50.6、Cairo 1.16.0，软件绘制，1x；
桌面 2560×1369，初始窗口 1100×760。完整统计每组重复三次；失败和未完成的
轮次单列。原始记录在 `/tmp/goui-sourceview-corpus-20261021/`。
其他平台、物理键盘、IME 组合输入、混合 DPI 与 GB 文件不在本轮实测范围。

### 多行 SourceView

使用 `desktop-v2-source-<文件>-1/2/3`，共 18 个窗口，各完成 57 项记录、全文恢复
和正常退出。源文件归一化后的整个模型均参与编辑；中部点击位置分别落在文件
字节数的 47.5%～54.5%，不是只编辑开头的小片段。每次拖动至少显示 4 个中间
尺寸帧，按最终更严格的“松手之前两帧”条件复核也全部通过。

首个文本像素出现时间。需要后续区分几何准备、分析推进和着色失效。

没有中间尺寸帧，不是字节/撤销校验失败。两控件保留各自默认字体，不能据此推导

### 真实窗口宽高变化

下表每格为“松手至就绪，中位数 / 最大值；操作期间最长事件间隔”，单位 ms。
每种尺寸变化包括缩小/恢复各三次，共 6 个样本。拖动本身约 0.5 秒，不混入松手后
等待。右下角拖动单列，不拿它代替单独改变宽/高。

| 场景 | 只改宽度 | 只改高度 | 同时改宽高 |
| --- | ---: | ---: | ---: |
| SourceView，54 MB JSON | 212 / 327；156 | 58 / 93；45 | 216 / 316；104 |
| SourceView，128 KB 单段落 | 509 / 543；323 | 46 / 76；46 | 518 / 676；339 |
| TextView，128 KB 单段落 | 602 / 1102；556 | 579 / 1052；550 | 576 / 1019；543 |

SourceView 单段落改变高度不需改变换行宽度，表现较好；改变宽度依然触发数百毫秒
的同步工作。它每次拖动中只观察到两次中间尺寸更新，属于最低限度通过，不能
称为流畅。TextView 三轮共 18 次拖动均在松手前观察到 0 次尺寸更新，故明确失败；
就绪后最终尺寸、光标、文本与全文恢复检查仍正确。TextView 的高度变化也有同类
停顿，需要核对是否因上层重复 Measure/宽度切换导致重新排版。

这些操作中的最大屏幕采样间隔，多行语料为 19～32 ms，两个单段落组分别为
27 ms、22 ms，明显小于上述数百毫秒/秒级停顿；不是观察进程停采导致的全部现象。

### 未完成与待处理要求

- TextView 的 54 MB 派生 JSON：在显式最小尺寸条件下，初始窗口 120 秒仍未读到
  可操作状态条，未进入任何编辑/缩放动作。记为前置失败，不计入操作延迟统计；
  后续同样的大文档重复轮次跳过，不能算作编辑通过。
- GOUI `gui/text_editor.go` 的 `measure` 在无约束高度下遍历逻辑行并同步测量。
  自然尺寸测量、视区准备和同宽测量复用应在 GUI 文本层处理，不能把策略移入

- SourceView 后续需处理长段落编辑/新宽度的同步停顿，以及 XML 视区准备长时间
  pending。通用 TextView 问题不能靠本控件绕过框架私有实现修复。
- 1 MiB 剪贴板失败与 INCR 能力边界见前文，本轮不提供其性能结论。

## 修正后的结果

以下为同一 Linux/Pango/Software/1x 环境、同一输入和正常桌面输入路径的后续修正。
SourceView 已按功能提交 `b631fce`、`6d80b4a`、`ea3b079`、`fd29b5a`、`33ac118`；
GOUI 已提交 `f9cc538`、`e1e0110`、`c051d82`、`b50da4f`。诊断程序 `fb577de`
提供中部编辑子集及可选分析器，性能统计均关闭分析器。上述基线失败保留，不再
将“只增加验证程序”或“未修改生产实现”视为当前状态。

### 已落实的修正

- GOUI TextView 的大文本自然尺寸查询采用已有高度估计，实际分配后的视区准备
  才确定换行宽度。仅改变高度不再切换至包含滚动条的外层宽度并重测正文。
- 同一逻辑段落内编辑保留此前折行高度估计，避免先缩成一行、隐藏滚动条，再因
  恢复滚动条切换宽度而二次重排。实际新尺寸仍由完整原生测量校正。
- TextView 保留最多四份近期被替换的大段落完整排版，附加源文本预算 1 MiB；
  只在全文及换行宽度完全一致时转移资源所有权。SourceView 在原有 128 项、8 MiB
  源文本缓存预算内采用同样的精确输入匹配。撤销、重做、退格恢复原文可以复用；
  不截断双向上下文，不推算替代原生坐标。模型、字体、样式和生命周期变化仍失效。
- Pango 导出簇坐标时减少逐簇重复查询当前行、字形 run 和无用 ink bounds，仍逐簇
  读取原生 logical bounds。完整混合脚本、RTL 控制符及占位符几何与旧实现一致。
- SourceView 从编辑增量映射未交叉的折叠范围，避免逐个调用 LineAt；相同的最终
  前景色范围不重复修改原生布局。标记匹配缓存无匹配结论；括号候选先检查自身行
  的词法类型，避免 XML 声明等非结构候选驱动大范围重分析及视区反复失效。

具体策略、键、预算、失效条件见 DesignLayout、DesignFolding、DesignMarkup、
DesignPairs 与 GOUI 的 DesignTextEditing、DesignTypography；这里记录验收结果。

### 端到端复测

每组独立启动三次并在正常关闭时逐字节恢复全文，单位 ms，`中位数 / 最大值`。

| 场景 | 修正前 | 修正后 | 验收边界 |
| --- | ---: | ---: | --- |
| TextView，54 MB JSON | 120 s 未进入编辑 | 输入 56 / 84，退格及 Delete 60 / 101 | 三轮完整 57 项、六种尺寸拖动、全文校验通过 |
| TextView，128 KB 单段落，仅改高 | 579 / 1052 | 62 / 84 | 松手至就绪；六次拖动均有中间帧 |
| SourceView，XML，中部滚动至非 pending | 36500～37240 | 262～325 | 三轮完整 57 项通过；不将原 pending 等待描述为连续冻结 |
| SourceView，128 KB 单段落，输入 | 345 / 390 | 302 / 326 | 全新内容仍有同步原生测量 |
| SourceView，同上，退格及 Delete | 361 / 380 | 64 / 80 | 可命中完整旧输入的场景 |
| SourceView，同上，撤销及重做 | 362 / 657 | 65 / 151 | 同宽完整测量缓存；不是近似重排 |

以上对应仓库外记录 `optimized-text-github-api-4x.json-*`、
`optimized-text-paragraph-128k.txt-*`、`final-lexical-source-opengl.xml-*`、
`final-history-source-paragraph-128k.txt-*`。TextView 的单段落宽度及角部拖动仍未
满足“松手前至少两帧”的响应要求；高度修正不代表宽度重排已解决。

另按用户实际单行 JSON 验证 TextView：157,862 bytes、157,830 runes、一个逻辑行，
SHA-256 `7baa22a894b415fdc3425c94f8a541d0ded8f77965541c46af3c95a3364c798b`。
通过真实滚动条跳到中部并点击（约字节 77,601），三轮各完成 16 条中部编辑记录，
每轮脚本及窗口退出码均为 0，全文校验通过。输入文件只读，未保存修改。

记录为 `user-json-middle-text-before-*`、`user-json-middle-text-history-*`。
其中独立的分析器实验确认此前输入会做两轮完整尺寸及簇坐标测量，撤销可达三轮；
修正后全新输入只需一轮，但该轮依然可能约 550 ms。**全新长段落内容和新宽度的
同步原生换行仍未解决**，不能以命中历史缓存的 60 ms 宣称全部编辑流畅。
一轮 `user-json-text-after` 受并行既有窗口测试抢焦点影响而中断，无正常关闭全文
校验，明确不计入通过轮次。
